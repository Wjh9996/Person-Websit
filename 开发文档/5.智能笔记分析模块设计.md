# 智能笔记分析模块设计（v1）

> 配套：数据库设计见 `4.数据库设计.md`（其中 `note_analysis`/`async_task` 为「接大模型笔记分析」预留，本文件把预留变成可落地业务）。
> 范围：**仅笔记模块**。前端沿用现有页面架构，仅微调（新增分析按钮 + 分析面板）。
> 阶段：本文档完成设计；后端实现 / 前端微调待用户确认选型后执行。

---

## 一、模块定位与目标

在用户写完笔记后，一键触发大模型对笔记内容做**结构化智能分析**，帮助用户快速回顾、整理、提炼。

设计原则（与现有架构一致）：

| 原则 | 落地 |
|---|---|
| 不阻塞主流程 | 大模型响应 1~10s，**绝不同步阻塞笔记读写**；用 `async_task` + 线程池异步执行，前端轮询结果 |
| 可插拔模型 | 走 **OpenAI 兼容协议**，一套 client 可切换任意厂商（OpenAI / DeepSeek / 通义千问 / 智谱 / 月之暗面 / 本地 Ollama），不绑定厂商 |
| 无新强依赖 | Spring Boot 自带 `RestClient`，调 HTTP 无需加 jar |
| 配置脱敏 | API Key 走 `${LLM_API_KEY:}` 环境变量占位，真实 `application.yml` 已被 gitignore；`example` 同步补 `llm.*` 模板 |
| 结果可失效 | 笔记正文大改（`content_hash` 变）后，旧分析结果 `status=0`，下次分析重新生成 |
| 权限收口 | 触发分析 / 查看本人分析均校验 `note.user_id` 归属，杜绝越权看他人分析结果 |

## 二、功能范围（按优先级）

| 分析类型 `analysis_type` | 说明 | 产物（存 `note_analysis.result` JSON） | 优先级 |
|---|---|---|---|
| `summary` | AI 摘要 | `{summary: string}`（2~3 句，可回填 `note.summary`） | P0 |
| `keywords` | 关键词提取 | `{keywords: string[]}`（3~8 个，可一键加为 `note.tags`） | P0 |
| `category` | 分类建议 | `{category: string, reason: string}` | P1 |
| `knowledge` | 知识点提炼 | `{points: string[]}`（核心考点/要点，面试向） | P1 |
| `similar`（进阶） | 相似笔记推荐 | 跨库语义检索，依赖向量库，**暂缓** | 阶段二 |

**v1 先做 `summary` + `keywords`，预留 `category`/`knowledge`/`similar`**（表结构已支持，加类型即可）。

## 三、整体架构

```
┌────────────┐   POST /api/notes/{id}/analyze    ┌──────────────────┐
│  前端页面   │ ───────────────────────────────▶ │  AnalysisController│ 需登录+归属校验
│ (笔记详情)  │ ◀──────── taskId ──────────────── │                  │
└────────────┘                                   └────────┬─────────┘
       │ 轮询 GET /api/analysis/tasks/{id}                 │ 建 async_task(pending)
       ▼                                                   ▼
┌────────────┐  提交任务                          ┌──────────────────┐
│ 分析面板    │ ◀──── task 状态/结果 ──────────── │  AsyncTaskService │ 写库 async_task
└────────────┘                                   └────────┬─────────┘
                                                        │ @Async 线程池
                                                        ▼
                                              ┌──────────────────────┐
                                              │  NoteAnalysisService  │
                                              │  · 读 note_content    │
                                              │  · 调 LlmClient       │──▶ 大模型(OpenAI兼容)
                                              │  · 写 note_analysis   │◀── 结果 JSON
                                              │  · 更新 task 状态     │
                                              └──────────────────────┘
```

> **为什么暂不上 MQ**：单实例 + 500 人在线，分析是低频操作（每人每天几次），`@Async` 线程池 + `async_task` 表轮询完全够。表结构已按「未来可换 MQ 消费者」设计——届时只把"线程池消费"换成"MQ 消费者消费同一张 `async_task` 表"，**不动任何表结构**。
> **为什么用轮询而非 WebSocket**：实现成本最低、前端改动最小，且分析结果对实时性不敏感（秒级延迟可接受）。后续可升级 SSE/WebSocket 推送。

## 四、LLM 接入设计（OpenAI 兼容协议）

**用 Spring `RestClient` 调 `/v1/chat/completions`**，请求体标准化，响应取 `choices[0].message.content`。

配置（`application.yml`，脱敏）：

```yaml
llm:
  base-url: ${LLM_BASE_URL:https://api.deepseek.com}   # 厂商地址
  api-key:  ${LLM_API_KEY:}                             # 真实值绝不入库
  model:    ${LLM_MODEL:deepseek-chat}
  timeout-seconds: 30
  max-tokens: 800
```

`application.yml.example` 同步补上述模板（进 git，指导他人部署）。

提示词（prompt）按 `analysis_type` 区分，统一要求**只返回 JSON**，便于解析：

- summary：`"用2-3句话概括以下笔记的核心内容，只返回JSON {\"summary\":\"...\"}"`
- keywords：`"提取3-8个关键词，只返回JSON {\"keywords\":[\"...\"]}"`
- knowledge：`"提炼笔记中的核心知识点/考点，只返回JSON {\"points\":[\"...\"]}"`

> 解析失败兜底：若模型返回非纯 JSON，用正则抽取首个 `{...}` 块；仍失败则 task 标记 `failed` 并记录 `error_msg`，前端提示"分析失败，可重试"。

## 五、数据库扩展（在 v2 基础上补方法，不改表结构）

`note_analysis` / `async_task` 表已满足。需给 Mapper 补方法：

**`NoteAnalysisMapper` 补：**
- `selectByNote(noteId)` → 查该笔记全部**有效**分析（`WHERE note_id=? AND status=1`）
- `invalidateByNote(noteId)` → 正文变更时 `UPDATE ... SET status=0 WHERE note_id=? AND status=1`

**`AsyncTaskMapper` 补：**
- `updateStatus(id, status, result, errorMsg)` → 任务流转 `processing/success/failed`
- `selectByBizId(type, bizId)` → 查某笔记最新分析任务

## 六、接口设计（新增，复用现有约定）

| 方法 & 路径 | 鉴权 | 说明 |
|---|---|---|
| `POST /api/notes/{id}/analyze?type=summary` | 登录 + 归属 | 触发分析，立即返回 `{taskId}`；type 可省略（默认全量分析 summary+keywords） |
| `GET  /api/notes/{id}/analysis` | 登录 + 归属 | 返回该笔记全部有效分析结果，按 `analysis_type` 聚合：`{summary, keywords, category, knowledge}` |
| `GET  /api/analysis/tasks/{taskId}` | 登录 | 轮询任务：`{taskId, status, result?, errorMsg?}`（status: pending/processing/success/failed） |
| `DELETE /api/notes/{id}/analysis` | 登录 + 归属 | 清除该笔记分析结果（可选） |

新增 `AnalysisController`（或并入 `NoteController` 的分析子路径）。返回统一 `ApiResult<T>`。

**触发-轮询时序：**
1. 前端点「AI 分析」→ `POST /analyze?type=summary`
2. 后端校验归属 → 建 `async_task(pending)` → 提交 `@Async` → 立即返回 `taskId`
3. 后台线程读 `note_content` → 调 `LlmClient` → 成功则写 `note_analysis` + task=`success`；失败 task=`failed`
4. 前端每 1.5s 轮询 `GET /tasks/{taskId}`，到 `success` 拉 `GET /analysis` 展示，`failed` 提示重试

## 七、结果失效策略（防脏数据）

`NoteServiceImpl.updateNote` 在正文变化（`content_hash` 改变）时：调用 `noteAnalysisMapper.invalidateByNote(id)` 把旧分析 `status=0`。下次用户点分析会重新生成；未点时旧结果不展示（`GET /analysis` 只取 `status=1`）。

## 十、安全与成本

- **API Key 脱敏**：仅环境变量注入，真实 `application.yml` 已被 `.gitignore` 忽略；`example` 补模板。
- **限流**：分析为低频操作，可在 `AnalysisController` 用简单计数（如每用户并发分析任务 ≤ 2）防滥用；未来上 Redis 限流。
- **超时**：`RestClient` 设 `timeout-seconds: 30`，超时 task 标记 `failed`，不阻塞。
- **成本**：500 人 × 每人每天 2 次分析 × ~500 token ≈ 50 万 token/天，国内厂商费用极低（约几元/天）；摘要/关键词用小模型即可。

## 十一、与后续分布式的衔接

本模块已为分布式预留：
- `async_task` 表天然支持"多实例抢任务"（未来加 `claimed_by` 字段 + `SELECT ... FOR UPDATE` 或 Redis 分布式锁即可）。
- `LlmClient` 与具体厂商解耦，换模型只改配置。
- 接 MQ 时，仅把「`@Async` 线程池消费」替换为「MQ 消费者消费同一张 `async_task` 表」，**表结构与接口不变**。
