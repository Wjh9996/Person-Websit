## 二、测试策略

### 2.1 分层策略（测试金字塔）

```
        ╱ E2E ╲           13 条  Cypress     主流程·真实浏览器（待执行）
      ╱ 接口回归 ╲         29 条  脚本化      契约·权限矩阵·数据隔离
    ╱   单元测试   ╲       58 条  JUnit/Vitest 逻辑分支·边界·异常路径
  ╱──────────────────╲
```

**为什么这样分配**

- 单元测试占大头（58/87）：权限判断、验证码策略这类逻辑分支多、执行快、不依赖外部环境，放在单测最划算；
- 接口层覆盖"跨模块契约"：前端拿到的字段、HTTP 状态码、权限矩阵，这些单测测不到；
- E2E 只覆盖主流程：慢且脆，只放最关键的"用户真正会走的路径"。

### 2.2 测试设计方法

| 方法 | 应用位置 | 举例 |
|---|---|---|
| **权限矩阵** | 数据隔离测试 | 角色（游客 / 登录用户 / 非作者 / 作者）× 操作（读 / 写 / 删 / 置顶 / 发布） |
| **等价类划分** | 验证码测试 | 有效码 / 错误码 / 过期码 / 已用码 / 无码 五个等价类 |
| **边界值分析** | 密码与限流 | 密码 5 位（拒绝）/ 6 位（通过）；重发间隔 59 秒（拒绝）/ 61 秒（允许） |
| **场景法** | 注册与重置流程 | 完整业务流：发码 → 取码 → 提交 → 验证结果 → 复用/重发 |
| **逆向测试** | 安全用例 | 越权访问、跨账号修改、验证码复用、暴力枚举（错 5 次作废） |
| **状态转换** | 验证码生命周期 | 未发送 → 已发送 → 已使用 / 已过期 / 已作废 |

### 2.3 重点测试领域

基于项目历史缺陷分布，测试资源向三个高风险区倾斜：

1. **多用户数据隔离**（曾发生 P0 越权缺陷）
2. **认证与验证码安全策略**（新功能，且是安全边界）
3. **前后端联调契约**（曾发生 CORS 403 缺陷）

### 5.2 P0 缺陷详情（历史最严重，现已修复并补测）

**P0-1 · 用户 A 的笔记出现在用户 B 的页面上**

- 现象：多用户场景下，列表与详情未校验数据归属，任何登录用户可查看甚至修改他人内容
- 根因：后端列表退回全表查询；详情接口无归属校验；`save`/`delete` 不校验归属
- 修复：列表强制带 `userId`（缺失时 `AND 1=0` 返回空集）；详情统一 `assertVisible` 收口；写操作逐一校验归属
- **回归防护**：`NoteServiceImplTest` 15 条 + 接口 D 组 4 条
- 教训：**"没传 userId 就查全部"是越权的根源**，缺失时应返回空集而非放宽条件

**P0-2 · 换账号后列表还是上一个人的数据**

- 现象：退出/切换账号后，前端仍展示上一位用户的数据
- 根因：store 只记录 `loaded` 布尔值，不足以判断"缓存是否属于当前用户"
- 修复：改为记录 `ownerId = 用户 id`，`watch(profile.id)` 变化时强制重载，登出清空
- **回归防护**：`note-scope.spec.ts` 4 条
- 教训：缓存 key 必须带用户维度，等同后端"缓存要按用户隔离"

### 5.3 P1 缺陷详情

**P1-1 · 登录后接口全部 403**

- 现象：未登录一切正常，登录后所有请求 403
- 根因：登录后请求带 `Authorization` → 触发 OPTIONS 预检 → 来源不在白名单 → 403；叠加 Vite 端口从 5180 漂移到 5181
- 修复：白名单改为 `http://localhost:*`；Vite 加 `strictPort`
- **回归防护**：接口 E 组预检用例
- 教训：**403 先怀疑预检，别急着查鉴权**

**P1-2 · 归属校验空指针**

- 现象：`updateNote` / `deleteNote` / `togglePinned` 中 `userId.equals(...)`，在 `userId` 为 null 时抛 NPE → 500
- 发现方式：编写权限单测时发现
- 修复：改为 `userId == null || !userId.equals(...)`，统一返回 403
- **回归防护**：`updateNote_withoutUser_forbidden` 用例

**P1-3 · 新增文件落盘到错误目录**

- 现象：`mvn compile` 退出码 0「看似通过」，启动却报 `No qualifying bean of type EmailCodeService`
- 根因：`EmailCodeServiceImpl.java` 被写入 `back/InterViewProject/...` 而非 `back/InterViewBacked/...`
- 修复：文件归位并清理错误目录
- 教训：**编译"通过"不等于文件在正确位置**，新增文件后应校验落盘路径

### 5.4 重复出现的同类问题

| 问题模式 | 出现次数 | 说明 |
|---|---|---|
| **新增的"登录前调用接口"被拦截器挡下** | 2 | `email-code`、`reset-password` 两次因未在 `JwtInterceptor` 白名单放行而返回 401 |
| 端口/路径配置写死导致环境失效 | 2 | CORS 白名单写死端口；Vite 端口漂移 |

> 第一条是本项目最应固化为规范的：凡是"用户还没登录就要调用"的接口，必须显式加白名单。

### 5.5 缺陷发现方式（定性）

| 缺陷 | 发现方式 |
|---|---|
| 跨账号越权、缓存串号 | **人工架构盘点**（做多用户场景推演时发现，接口测试当时未覆盖该场景） |
| 登录后 403、端口冲突、Maven 快照 | 联调与环境排查 |
| 消息乱序、全文检索失效、建表脚本清库 | 功能自测与数据核对 |
| 追问答非所问、token 失控 | AI 功能实测 |
| **归属校验空指针** | **编写权限单测时发现** |
| 文件落盘路径错误 | 服务启动时报 `No qualifying bean` |
| 登录前接口被拦截器挡下 | 接口实测返回 401 |

> 关键观察：两个 P0 缺陷（越权、缓存串号）都是**人工推演多用户场景**才发现的——它们在单用户测试下"跑得好好的"。
> 这说明自动化测试无法替代架构级评审，尤其在 AI 辅助开发场景下，AI 产出的是"按需求能跑的代码"，
> "换成第二个人来用会怎样"这类问题必须由人来问。这也是本项目把测试资源向数据隔离倾斜的原因。
