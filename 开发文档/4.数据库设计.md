# 数据库设计（重构版 v2）

> 配套建表脚本：`back/InterViewBacked/src/main/resources/schema.sql`（本文件 DDL 与其严格一致）
> 设计依据：`1.需求分析.md` 附一 P0、`500人在线笔记系统设计方案.md`、`3.接口文档.md`、当前后端实体与 Mapper 实际代码。
> 目标：支撑 500 人同时在线 + 消除水平越权/并发覆盖 + 列表查询去正文 + 为未来分布式（接大模型做笔记分析、对象存储、MQ 异步）预留扩展位。
> 范围：笔记系统为主；简历本次**只补安全字段、不重构功能**；用户表顺势补状态/角色。
> 阶段：本文件与 `schema.sql` 仅完成「数据库设计」，后端改造待定稿后进行。

## 一、设计目标与约束

| 目标 | 说明 |
|---|---|
| 多用户安全 | 所有业务数据带 `user_id`，写操作校验归属，杜绝水平越权（P0） |
| 并发正确 | 乐观锁 `version` 防并发编辑静默覆盖（P0） |
| 列表性能 | 正文垂直拆分到 `note_content`，列表查询单行从 ~10 KB 降到 ~200 B（P0） |
| 可回收 | 软删除 `deleted` + `deleted_at`，支持回收站 30 天恢复 |
| 可检索 | `title/summary` 建 ngram 全文索引，2.5 万篇内免 ES |
| 可扩展 | 预留大模型分析、异步任务、对象存储、分享链接，未来加 MQ/分库分表不推倒重来 |
| 前端不动 | 页面架构保持；`note.tags` 仍为数组（冗余展示），前端仅微调接口 |

## 二、设计原则（决定表结构长什么样）

| 原则 | 说明 | 反例 |
|---|---|---|
| **① 主键全局唯一、不依赖自增** | 全部 `VARCHAR(64)`（UUID / 雪花 ID），应用层生成 | `AUTO_INCREMENT` 在分库分表后必然冲突 |
| **② 物理外键最小化** | 仅保留 `note_content→note` 的级联删除外键；其余关联（标签、分享等）用应用层保证 | 外键会让分库分表、迁移、批量清理变棘手 |
| **③ 所有业务表带 `user_id`** | 既是权限隔离基础，也是未来分片键 | 无 `user_id` 无法按用户分片 |
| **④ 大字段垂直拆分** | 正文单独表，列表查询不触碰 | 正文放主表拖垮带宽 |
| **⑤ 软删除统一** | `deleted` + `deleted_at`，回收站可恢复 | 物理删除误删不可恢复 |
| **⑥ 时间用 `DATETIME`** | 避免 2038 问题、不受时区影响 | `TIMESTAMP` 上限 2038-01-19 |
| **⑦ 状态字段留扩展位** | `status`/`role` 用 `TINYINT`/`VARCHAR`，不堆布尔 | 后续加「草稿/归档/封禁」需改字段 |

> 关于原则②：旧版设计「完全不用外键」。本版仅对 1:1 且强一致的 `note_content` 保留级联外键（删笔记自动删正文，减少孤儿数据）；其余多对多/弱关联用逻辑外键，平衡一致性与未来分片灵活性。

## 五、详细表设计（DDL 与 schema.sql 一致）

### 5.1 `user` 用户表（改造）
```sql
CREATE TABLE `user` (
    id            VARCHAR(64)  NOT NULL PRIMARY KEY,
    username      VARCHAR(64)  NOT NULL,
    password      VARCHAR(100) NOT NULL,
    nickname      VARCHAR(64),
    email         VARCHAR(128),
    avatar        VARCHAR(512),            -- 改为 URL（未来走对象存储），原为 VARCHAR(10) 占位
    bio           VARCHAR(500),
    role          VARCHAR(20)  NOT NULL DEFAULT 'user',  -- user / admin
    status        TINYINT(1)   NOT NULL DEFAULT 1,        -- 1 正常 0 禁用
    deleted       TINYINT(1)   NOT NULL DEFAULT 0,
    last_login_at DATETIME,
    created_at    DATETIME,
    updated_at    DATETIME,
    UNIQUE KEY uk_username (username)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4;
```
相对旧表：补 `role`（管理/分享权限）、`status`（封禁）、`deleted`（软删）、`last_login_at`（限流/审计）、`updated_at`；`avatar` 扩到 512 存 URL。

### 5.2 `note` 笔记元数据表（核心重构）
```sql
CREATE TABLE `note` (
    id           VARCHAR(64)  NOT NULL PRIMARY KEY,
    user_id      VARCHAR(64)  NOT NULL,
    title        VARCHAR(200) NOT NULL,
    summary      VARCHAR(500),
    category     VARCHAR(32),
    tags         VARCHAR(1000),                  -- 标签 JSON 数组（展示冗余；真相源见 note_tag_rel）
    pinned       TINYINT(1)   NOT NULL DEFAULT 0,
    views        INT          NOT NULL DEFAULT 0,
    version      INT          NOT NULL DEFAULT 0,            -- 乐观锁
    content_hash VARCHAR(64),                               -- 正文 MD5，后端去重
    deleted      TINYINT(1)   NOT NULL DEFAULT 0,            -- 软删除
    deleted_at   DATETIME,
    created_at   DATETIME,
    updated_at   DATETIME,
    INDEX idx_user_updated (user_id, updated_at),
    INDEX idx_user_category (user_id, category),
    INDEX idx_user_deleted  (user_id, deleted),
    FULLTEXT INDEX ft_title_summary (title, summary) WITH PARSER ngram
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4;
```
- **去掉 `content`**：列表单行 ~10 KB → ~200 B。
- **`content_hash`**：自动保存先比对 MD5，相同直接返回不写库。
- **`version`**：更新 `WHERE version = #{expected}`，0 行返回 409。
- **软删除**用 `deleted`+`deleted_at`：1 正常、回收站查 `deleted=1`、定时任务清 `deleted_at < NOW()-30d`。

### 5.3 `note_content` 笔记正文表（新增）
```sql
CREATE TABLE `note_content` (
    note_id VARCHAR(64) NOT NULL PRIMARY KEY,
    content LONGTEXT,
    CONSTRAINT fk_content_note FOREIGN KEY (note_id) REFERENCES `note`(id) ON DELETE CASCADE
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4;
```
仅详情接口按主键单查；删笔记级联删正文，无孤儿数据。

### 5.4 `tag` + `note_tag_rel`（标签管理）
```sql
CREATE TABLE `tag` (
    id         VARCHAR(64) NOT NULL PRIMARY KEY,
    user_id    VARCHAR(64) NOT NULL,
    name       VARCHAR(50) NOT NULL,
    color      VARCHAR(20),
    created_at DATETIME,
    UNIQUE KEY uk_user_name (user_id, name),
    INDEX idx_user (user_id)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4;

CREATE TABLE `note_tag_rel` (
    note_id VARCHAR(64) NOT NULL,
    tag_id  VARCHAR(64) NOT NULL,
    PRIMARY KEY (note_id, tag_id),
    INDEX idx_tag (tag_id),
    CONSTRAINT fk_rel_note FOREIGN KEY (note_id) REFERENCES `note`(id) ON DELETE CASCADE,
    CONSTRAINT fk_rel_tag  FOREIGN KEY (tag_id)  REFERENCES `tag`(id) ON DELETE CASCADE
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4;
```
- 由旧 `note.tags` JSON 规范化而来：标签云直接 `GROUP BY`、支持重命名/合并/删除、支持按标签筛选。
- **双写约定**：`note.tags` 保留为「展示冗余」数组（前端列表零改动），`note_tag_rel` 为「管理真相源」；service 事务内同步两者。
- 数据量：2.5 万篇 × 3 标签 ≈ 7.5 万行，很小。

### 5.5 `note_share` 分享只读链接（新增，阶段二功能）
```sql
CREATE TABLE `note_share` (
    id         VARCHAR(64) NOT NULL PRIMARY KEY,
    note_id    VARCHAR(64) NOT NULL,
    token      VARCHAR(64) NOT NULL,
    created_by VARCHAR(64) NOT NULL,
    expires_at DATETIME,
    created_at DATETIME,
    UNIQUE KEY uk_token (token),
    INDEX idx_note (note_id)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4;
```
他人凭 token 只读访问单篇，绕过 `user_id` 归属校验（独立鉴权）。

### 5.6 `note_analysis` 大模型分析结果（预留）★
```sql
CREATE TABLE `note_analysis` (
    id            VARCHAR(64) NOT NULL PRIMARY KEY,
    note_id       VARCHAR(64) NOT NULL,
    user_id       VARCHAR(64) NOT NULL,
    analysis_type VARCHAR(32) NOT NULL,          -- keywords / summary / category / similar
    result        JSON,                          -- 结构化分析结果
    model         VARCHAR(64),                   -- 模型标识
    status        TINYINT(1) NOT NULL DEFAULT 1, -- 1 有效 0 失效（内容大改后旧分析失效）
    created_at    DATETIME,
    updated_at    DATETIME,
    INDEX idx_note_type (note_id, analysis_type)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4;
```
为「接大模型做笔记分析」预留：`result` 用 JSON 适配不同分析类型；模型升级只加 `analysis_type`，不破坏表结构。

### 5.7 `async_task` 异步任务队列（预留）★
```sql
CREATE TABLE `async_task` (
    id          VARCHAR(64) NOT NULL PRIMARY KEY,
    user_id     VARCHAR(64),
    type        VARCHAR(32) NOT NULL,            -- ANALYSIS / EXPORT / ...
    biz_id      VARCHAR(64),                     -- 关联业务主键（如 note_id）
    status      VARCHAR(16) NOT NULL,            -- pending / processing / success / failed
    payload     JSON,
    result      JSON,
    error_msg   VARCHAR(500),
    retry_count INT NOT NULL DEFAULT 0,
    created_at  DATETIME,
    updated_at  DATETIME,
    INDEX idx_status (status),
    INDEX idx_user_type (user_id, type)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4;
```
为 MQ/大模型/导出预留：当前同步写库即可；未来「保存笔记 → 投 async_task → 消费者调大模型 → 写回 note_analysis」平滑升级到 MQ。

### 5.8 `file` 对象存储文件元信息（预留）★
```sql
CREATE TABLE `file` (
    id         VARCHAR(64) NOT NULL PRIMARY KEY,
    user_id    VARCHAR(64) NOT NULL,
    note_id    VARCHAR(64),
    bucket     VARCHAR(64),
    object_key VARCHAR(255) NOT NULL,            -- 对象存储 key（禁止 base64 存正文）
    url        VARCHAR(512),
    name       VARCHAR(255),
    ext        VARCHAR(16),
    size       BIGINT NOT NULL DEFAULT 0,
    mime       VARCHAR(64),

) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4;
```
图片必须走对象存储；正文只存 `file.url`，本表存元信息便于审计/清理/CDN。

### 5.9 `resume` 简历表（仅补安全字段）

## 七、数据迁移方案

### 开发阶段（直接重建）
新版 `schema.sql` 开头 `SET FOREIGN_KEY_CHECKS=0` + `DROP TABLE IF EXISTS` + 重建。后端同步后启动，`DataInitializer` 重新 seed（种子笔记/简历填 `user_id=admin`、`version=0`、正文写 `note_content`）。

### 生产环境（增量 ALTER，保留数据）
```sql
-- note
ALTER TABLE note
  ADD COLUMN user_id VARCHAR(64) NOT NULL DEFAULT '',
  ADD COLUMN version INT NOT NULL DEFAULT 0,
  ADD COLUMN content_hash VARCHAR(64),
  ADD COLUMN deleted TINYINT(1) NOT NULL DEFAULT 0,
  ADD COLUMN deleted_at DATETIME,
  ADD INDEX idx_user_updated (user_id, updated_at),
  ADD INDEX idx_user_category (user_id, category),
  ADD INDEX idx_user_deleted (user_id, deleted),
  ADD FULLTEXT INDEX ft_title_summary (title, summary) WITH PARSER ngram;
CREATE TABLE note_content (note_id VARCHAR(64) PRIMARY KEY, content LONGTEXT,
  CONSTRAINT fk_content_note FOREIGN KEY (note_id) REFERENCES note(id) ON DELETE CASCADE);
INSERT INTO note_content (note_id, content) SELECT id, content FROM note;
ALTER TABLE note DROP COLUMN content;

-- resume
ALTER TABLE resume
  ADD COLUMN user_id VARCHAR(64) NOT NULL DEFAULT '',
  ADD COLUMN version INT NOT NULL DEFAULT 0,
  ADD COLUMN deleted TINYINT(1) NOT NULL DEFAULT 0,
  ADD INDEX idx_user (user_id);

-- user
ALTER TABLE user
  MODIFY COLUMN avatar VARCHAR(512),
  ADD COLUMN role VARCHAR(20) NOT NULL DEFAULT 'user',
  ADD COLUMN status TINYINT(1) NOT NULL DEFAULT 1,
  ADD COLUMN deleted TINYINT(1) NOT NULL DEFAULT 0,
  ADD COLUMN last_login_at DATETIME,
  ADD COLUMN updated_at DATETIME;

-- 新建扩展表：tag / note_tag_rel / note_share / note_analysis / async_task / file
-- （DDL 见第五节，直接 CREATE TABLE 即可）

-- 回填归属（现有数据归 admin）
UPDATE note   SET user_id = (SELECT id FROM user WHERE username='admin' LIMIT 1) WHERE user_id='';
UPDATE resume SET user_id = (SELECT id FROM user WHERE username='admin' LIMIT 1) WHERE user_id='';

-- 标签规范化（应用层脚本）：解析 note.tags JSON → 写 tag + note_tag_rel
```
> 建议后端改造时用 Flyway / Liquibase 管理迁移脚本，避免手工 SQL 导致环境不一致。

## 八、容量估算

| 项 | 估算 |
|---|---|
| 用户数 | 500 |
| 笔记总数 | 500 × 50 = **2.5 万篇** |
| `note` 表 | 2.5 万 × ~200 B ≈ **5 MB** |
| `note_content` | 2.5 万 × 10 KB ≈ **250 MB** |
| `note_tag_rel` | ~7.5 万行 ≈ 3 MB |
| 三年（3 倍） | ~800 MB |

**结论**：单库单表完全够，**不需要分库分表**。设计上已预留分片能力（全带 `user_id`、主键不依赖自增），真正分片是十万级用户之后的事。

## 九、未来扩展预留

### 9.1 搜索（500 人刚需）
`MATCH(title, summary) AGAINST (? IN NATURAL LANGUAGE MODE)`，仅搜 title/summary；超 10 万篇再上 ES + MQ 同步。

### 9.2 读写分离
写主库、读从库；自动保存后立刻读详情应强制走主库（防主从延迟），或用 Redis 兜底。

### 9.3 分库分表（十万级之后）
- 分片键 `user_id`（所有查询带它，无跨片 JOIN）
- 主键 UUID/雪花已全局唯一，跨片不冲突
- 无物理外键（除 `note_content`），便于迁移

### 9.4 接入大模型（预留，本次不实现）
流程：前端触发 → 写 `async_task`(status=pending) → 发 MQ → AI 服务消费 → 调大模型 → 回写 `note_analysis`(result) → 前端轮询/WebSocket 推送。AI 完全异步解耦，响应慢不阻塞笔记主流程。

### 9.5 对象存储 / CDN
图片走 `file` 表 + 对象存储 key，多实例共享，杜绝本地磁盘不一致。

## 十、与前后端对接 & 后端设计落地情况

**前端已完成（对齐新接口）**：`note.tags` 仍是数组，`Note` 类型不变；service 层已改调新接口，页面与 store 仅微调（符合「前端微调」）。要点：
1. 列表接口不再返回正文 `content`，store 新增 `fetchNoteDetail(id)` —— 在详情/编辑页单独拉取完整笔记（含 `content`）并合并回列表条目，供 `getNoteById` 复用。
2. `filteredNotes` 与 `NoteCardComponent` 去掉对列表 `content` 的硬依赖：搜索仅匹配标题/摘要，卡片阅读时长回退到 `summary`；`excerpt / readingTime / renderMarkdown` 统一做 `undefined` 容错，避免列表渲染崩溃。
3. 写操作（`createNote / updateNote / removeNote / togglePinned`，以及简历 `createResume / saveResume / removeResume`）在 `NoteEditorView / NoteDetailView / ResumeView` 全量包 `try/catch`，复用 `getErrorMessage(e)` 把 401/403/409/404 等后端文案透出给用户；并补 `error-tip` 提示条。
4. 校验：`vue-tsc --build` 类型检查通过，`vite build` 生产构建通过。

**后端已完成（对齐新表）**
1. 实体：新增 `NoteContent` / `Tag` / `NoteTagRel` / `NoteShare` / `NoteAnalysis` / `AsyncTask` / `File`；`User`/`Note`/`Resume` 补齐 `userId`/`version`/`deleted`/`deletedAt`/`contentHash`/`role`/`status`/`lastLoginAt` 等字段（Jackson3 `transient` 隐藏密码不变）。
2. Mapper（XML）：`note` 列表 SQL 去 `content`、按 `user_id+updated_at` 排序；详情 `note_content` 单查；更新带 `version` 条件（`WHERE version=#{version}`，0 行 → 409）；软删除 `deleted=1`；tag 云 `GROUP BY` 聚合；其余 4 张预留表用注解 Mapper 建好 CRUD 桩。
3. Service：`NoteServiceImpl` 写操作校验归属（非本人 → 403）+ 乐观锁（版本冲突 → 409）+ `content_hash` 去重（字段均无变化直接返回不写库）+ 标签事务双写（`note.tags` 冗余 + `note_tag_rel` 真相源）；`UserServiceImpl` 注册补 `role/status/deleted`、`login` 更新 `last_login_at`；`ResumeServiceImpl` 补 `user_id/version`、保存走乐观锁。
4. Controller：写操作（`POST/PUT/DELETE/PATCH /api/notes`、`POST /api/resumes`）从 `JwtInterceptor` 取 `userId` 透传；读接口（`GET` 列表/详情/标签/浏览量）公开。`GET /api/notes` 新增可选 `userId` 查询参数（个人中心视图，仅返回该用户笔记）。
5. `DataInitializer`：种子笔记/简历填 `user_id=admin`、`version=0`、正文拆写 `note_content`、标签规范化入 `tag`+`note_tag_rel`、`content_hash` 由 `HashUtils.md5Hex` 计算。
6. `application.yml`：`spring.sql.init.mode: always`（开发期启动即套用 v2 脚本并重新 seed；生产改 `never` + 增量迁移）。

**关键设计决策（与数据库设计一致）**
- **读公开 / 写鉴权**：笔记列表与详情对游客公开（个人作品集属性），但所有写操作强制校验 `user_id` 归属，杜绝水平越权；真正多租户隔离时再把列表按 `userId` 收口即可（字段已就绪）。
- **软删除即回收站**：`deleteNote` 仅置 `deleted=1`，正文与标签保留；后续可加「30 天自动清理」定时任务（见 9.x）。

### 10.1 简历数据隔离 + 游客脱敏模板（已落地）

**诉求**：新注册用户绝不能看到/篡改站长的简历；未登录游客看到的是一份不含私人联系方式的「模板简历」，登录后只看到自己创建的简历。

**实现要点**
- **`JwtInterceptor` 改造（核心根因修复）**：此前仅对「需鉴权请求（非 GET / 非 `/api/auth/me` / 非 `/api/users/**`）」才解析令牌并设置 `userId`。这导致已登录用户访问公开 `GET /api/resumes` 时 `userId` 为 null，错误地落入模板分支（新用户看到 admin 简历的直接根因）。改为：**只要请求携带合法 Bearer 令牌，无论 GET 与否都 `request.setAttribute("userId", ...)`；无令牌或令牌失效则 `userId` 保持 null（走模板/匿名分支）**。对需鉴权接口，若 `userId == null` 仍返回 401（HTTP 200 + `code:401`，与全局异常处理器一致）。
- **`ResumeServiceImpl.getSnapshot(userId)`**：
  - `userId == null` → `buildPublicTemplate()`：取站长账号 `username=admin` 的全部简历，`sanitize()` 抹掉 `basicInfo.phone / email`（保留姓名/学校/技能/项目等可公开作品集内容）。
  - `userId != null` → `buildSnapshot(selectByUserId(userId))`：**只返回该用户自己的简历**，天然做到水平隔离。
- **写操作归属校验**：`saveResume / deleteResume` 先 `selectById`，若 `!userId.equals(resume.getUserId())` 抛 `BusinessException(403, "无权操作该简历")`；`createResume` 落 `user_id = 当前用户`。
- **前端**：`useResumeStore.loadResumes()` 做身份感知缓存（`loadedFor: 'guest' | 'user'`），登录态翻转通过 `watch(userStore.isLogin)` 自动重载快照，游客模板与本人简历不会串。

**端到端验证（Node fetch 脚本，已全部通过）**
1. 游客 `GET /api/resumes` → 3 份站长模板，`phone/email` 均为空 ✅
2. 新用户登录后 `GET /api/resumes` → 空列表（看不到站长简历）✅
3. 新用户 `PUT / DELETE` 站长简历 → `{"code":403,"message":"无权操作该简历"}` ✅
4. 新用户自建简历 → `GET` 只看到自己 1 份（含完整私人信息）→ 可正常 `PUT / DELETE` 本人简历 ✅
