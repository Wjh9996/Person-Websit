# AI 助手：基于自己笔记的知识库问答（RAG）

> 目标：每个用户拥有一个"私人知识库 AI 助手"——只能检索**自己写的笔记**，基于笔记内容作答并给出引用来源。
> 定位：笔记模块的 AI 增强，与已有的「单篇笔记智能分析」互补（那是对一篇笔记做摘要/关键词，这是跨笔记检索问答）。

---

## 一、先说结论（技术选型与为什么）

| 决策项 | 选择 | 理由 |
|---|---|---|
| 召回方式 | **MySQL 全文检索（ngram）** | 零新增组件，复用现有 `ft_title_summary` + 新增 `note_content.ft_content`；几十～几百篇笔记量级够用 |
| 知识库范围 | **仅当前用户自己的笔记** | 隐私边界最清晰，与「我的笔记」口径一致，天然满足可见性隔离 |
| 回答方式 | **同步返回** | 与现有「AI 分析」任务模式一致，实现稳、前端改动小；未来可平替 SSE |
| 会话历史 | **持久化，支持多轮** | 新增 `chat_session` / `chat_message`，可继续追问、可回看 |
| 大模型 | **DeepSeek（OpenAI 兼容）** | 复用已有 `LlmClient`，不引入新 SDK |

**没有引入向量数据库**：500 篇以内的个人笔记，全文检索 + 大模型重排足够；
Embedding 向量检索虽语义更准，但要额外增加向量存储与离线建索引流程，属于"过早优化"。
真到需要时，只需把 `AssistantServiceImpl.recall()` 换成向量检索即可，**上层组装 Prompt 的逻辑不用动**。

## 二、整体流程（RAG 三段式）

```
用户提问
  │
  ├─ ① 落库 user 消息（保证问答历史完整，即使后续失败）
  │
  ├─ ② 召回 Recall：note + note_content 全文检索
  │      SELECT ... WHERE n.user_id = ?            ← 强制带用户，杜绝越权
  │        AND (MATCH(n.title,n.summary) AGAINST(kw)  * 3
  │          OR MATCH(c.content)         AGAINST(kw))
  │      ORDER BY score DESC LIMIT 5
  │      └─ 全文索引不可用 → 退化为 LIKE 兜底
  │
  ├─ ③ 生成 Generate：历史对话 + 参考笔记 + 问题 → DeepSeek
  │      system: 只依据笔记作答，找不到要明说，输出 JSON
  │      └─ 单篇正文截断 2500 字，控制 token
  │
  └─ ④ 落库 assistant 消息（含 refs 引用）+ 更新会话标题
```

三个细节（都是实测踩出来的）：

1. **追问召回**：短句"再详细说说第二点"检索不到东西，因此当问题 < 12 字且存在上一轮问题时，召回关键词拼接"上一轮问题 + 本轮问题"。
2. **消息排序**：`DATETIME` 默认只到秒，同一秒内的消息会乱序 → `chat_message.created_at` 用 `DATETIME(3)` 毫秒精度。
3. **Prompt 放宽**：纯追问时参考笔记可能不相关，允许模型依据**历史对话**继续作答，并要求说明"依据上一轮对话"，避免一律答"笔记里没有提到"。

## 三、数据库变更

```sql
-- 会话
CREATE TABLE chat_session (
    id VARCHAR(64) PRIMARY KEY,
    user_id VARCHAR(64) NOT NULL,
    title VARCHAR(200) NOT NULL DEFAULT '新对话',
    deleted TINYINT(1) NOT NULL DEFAULT 0,
    created_at DATETIME(3),
    updated_at DATETIME(3),
    INDEX idx_user_updated (user_id, updated_at)
);

-- 消息
CREATE TABLE chat_message (
    id VARCHAR(64) PRIMARY KEY,
    session_id VARCHAR(64) NOT NULL,
    user_id VARCHAR(64) NOT NULL,
    role VARCHAR(16) NOT NULL,          -- user / assistant
    content MEDIUMTEXT,
    refs JSON,                          -- [{noteId,title,score}] 引用溯源
    created_at DATETIME(3),
    INDEX idx_session_created (session_id, created_at),
    CONSTRAINT fk_msg_session FOREIGN KEY (session_id) REFERENCES chat_session(id) ON DELETE CASCADE
);

-- 知识库召回：正文全文索引（ngram）
ALTER TABLE note_content ADD FULLTEXT INDEX ft_content (content) WITH PARSER ngram;
ALTER TABLE chat_message MODIFY COLUMN created_at DATETIME(3);
```

> 完整 DDL 已并入 `back/InterViewBacked/src/main/resources/schema.sql`；
> 生产环境请走 `开发文档/4.数据库设计.md` 第七章的增量迁移，不要直接跑开发版脚本（会 DROP 重建）。

## 四、后端接口（`/api/assistant`，全部需登录）

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/assistant/sessions` | 我的会话列表（按更新时间倒序） |
| POST | `/api/assistant/sessions` | 新建会话，body 可选 `{title}` |
| DELETE | `/api/assistant/sessions/{id}` | 删除会话（软删除，校验归属） |
| GET | `/api/assistant/sessions/{id}/messages` | 会话消息（正序） |
| POST | `/api/assistant/sessions/{id}/ask` | 提问，body `{question}`，同步返回 `{answer, refs, fromKnowledgeBase}` |

安全要点：
- GET 接口也要登录：`JwtInterceptor` 对 GET 放行，所以 Controller 用
  `@RequestAttribute(value="userId", required=false)` 取身份后**手动判空抛 401**；
- 会话/消息都校验 `user_id` 归属，越权访问返回 403；
- 召回 SQL 强制 `WHERE n.user_id = ?`，A 用户不可能检索到 B 的笔记。

## 七、后续可演进（按收益排序）

1. **流式输出（SSE）**：答案逐字返回，体验提升最明显；后端把同步 `ask` 换成 `SseEmitter`，前端改成增量追加。
2. **召回优化**：笔记切片（chunk）+ 命中段落高亮，避免整篇塞入；长笔记效果更好。
3. **向量检索**：笔记上千或语义召回明显不足时，加 Embedding + 向量库，替换 `recall()` 即可。
4. **引用可跳转定位**：点击引用直接跳到笔记详情并滚动到命中段落。
5. **知识库范围开关**：允许勾选"同时参考讨论广场的公开笔记"。
