# 500 人在线笔记记录系统：设计方案

> 目标：在现有 Vue3 + Spring Boot + MyBatis 框架基础上，支撑约 **500 人同时在线**
> 记录、编辑自己的笔记。
> 前置：本文假设「数据归属改造 + 乐观锁 + 列表查询去正文」等 P0 问题已完成
> （见 `上线架构演进方案.md` 与 `1.需求分析.md` 附一）。

---

## 一、结论先行

**500 人在线的笔记系统：单机 Spring Boot + MySQL + Redis 可以支撑，但Redis 在这个量级开始有真实收益，MQ 仍然不是必需品。**

与 50 人方案的关键差异：

| 维度 | 50 人（简历） | 500 人（笔记） |
|---|---|---|
| 写入特征 | 偶发点击保存 | **自动保存，持续高频写** |
| Redis | 收益接近于零 | **有真实收益**（缓存列表/详情、限流） |
| 搜索 | 不需要 | **刚需**（数万篇笔记） |
| 大字段 | 不适用 | **必须处理**（正文不能进列表查询） |
| 多实例 | 不需要 | 建议 2 实例做高可用（非性能必需） |
| MQ | 不需要 | 可选（接 ES 后才有强需求） |

**真正的技术难点不是并发量，而是"自动保存"带来的持续写压力，以及数万篇笔记的检索。**

## 二、容量估算：先算账再选型

### 2.1 请求量估算

- 500 人在线，假设同时**正在操作**的占 20%（约 100 人）
- **自动保存**：前端防抖后按每 5 秒 1 次 → 100 ÷ 5 = **约 20 QPS 持续写**
- **读请求**：列表 / 详情 / 搜索，按每人每 30 秒 1 次 + 浏览放大 → 峰值 **约 50～100 QPS 读**
- **峰值余量**：按 3 倍预留 → 设计目标 **写 60 QPS / 读 300 QPS**

> 对照：MySQL 单机轻松数千 QPS，Spring Boot（Tomcat 默认 200 线程）单机也能覆盖。
> **结论：性能上单机够用，瓶颈不在 QPS，而在下面几个具体陷阱。**

### 2.2 数据量估算

| 项 | 估算 |
|---|---|
| 笔记总数 | 500 人 × 50 篇 = **2.5 万篇** |
| 单篇大小 | Markdown 文本约 10 KB |
| 正文总量 | 2.5 万 × 10 KB ≈ **250 MB** |
| 三年增长 | 按 3 倍 → 约 750 MB |

> 250 MB 对 MySQL 毫无压力。**但如果把图片以 base64 存进正文，体积会暴涨 10 倍以上**——
> 图片必须走对象存储，这是第一个硬性约束。

## 三、笔记系统 vs 简历系统：四个新增难点

### 难点 1：自动保存带来持续写压力（最核心）

简历是"点一下保存"，笔记是"边打字边保存"。若处理不当：

- 每次输入都发请求 → 500 人可打出数千 QPS 的写请求
- 每次都整篇写入 → 数据库写放大，网络和磁盘 IO 压力剧增

### 难点 2：列表查询带出全文（当前代码已存在此问题）

`NoteMapper.xml` 的 `columns` 片段包含 `content`(LONGTEXT)，
`selectAll` 会把**全部笔记正文**一次性查出：

```xml
<sql id="columns">
    id, title, summary, content, category, tags, pinned, views, created_at, updated_at
</sql>
<select id="selectAll" resultType="Note">
    SELECT <include refid="columns"/> FROM note
</select>
```

单用户 50 篇 × 10 KB = 一次列表请求返回 **500 KB**；500 人同时刷列表，
带宽与 JVM 内存都会被吃掉。这是笔记类系统最典型的性能陷阱。

### 难点 3：搜索从"可选"变成"刚需"

2.5 万篇笔记，用户不可能靠翻页找内容。搜索必须做，且**不能用 `LIKE '%关键词%'`**
（全表扫描，2.5 万行 × 大字段必然慢）。

### 难点 4：单人多端编辑的冲突

同一用户在手机和电脑同时打开一篇笔记，比"多人协同"更常见。
需要版本号机制让后保存的一方感知到冲突，而不是静默覆盖。

## 四、数据模型改造

### 4.1 垂直拆分：正文与元数据分离

```sql
-- 元数据表（列表页只查这个，轻量）
CREATE TABLE `note` (
    id          VARCHAR(64)  NOT NULL PRIMARY KEY,
    user_id     VARCHAR(64)  NOT NULL,
    title       VARCHAR(200) NOT NULL,
    summary     VARCHAR(500),
    category    VARCHAR(32),
    tags        VARCHAR(500),
    pinned      TINYINT(1)   DEFAULT 0,
    views       INT          DEFAULT 0,
    version     INT          NOT NULL DEFAULT 0,
    deleted     TINYINT(1)   DEFAULT 0,
    created_at  DATETIME,
    updated_at  DATETIME,
    INDEX idx_user_updated (user_id, updated_at),
    INDEX idx_user_category (user_id, category)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4;

-- 正文表（只在打开详情时按 id 单条查询）
CREATE TABLE `note_content` (
    note_id  VARCHAR(64) NOT NULL PRIMARY KEY,
    content  LONGTEXT,
    CONSTRAINT fk_content_note FOREIGN KEY (note_id) REFERENCES `note`(id) ON DELETE CASCADE
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4;
```

**收益**：列表查询不再触碰大字段，单行从 ~10 KB 降到 ~200 B，
一次列表响应从 500 KB 降到 **10 KB 以内**。

### 4.2 Mapper 拆成两个查询

```xml
<!-- 列表：不含正文 -->
<select id="selectListByUserId" resultType="Note">
    SELECT id, title, summary, category, tags, pinned, views, version, updated_at
    FROM note
    WHERE user_id = #{userId} AND deleted = 0
    ORDER BY pinned DESC, updated_at DESC
    LIMIT #{offset}, #{size}
</select>

<!-- 详情：连正文 -->
<select id="selectDetailById" resultMap="noteWithContent">
    SELECT n.*, c.content
    FROM note n LEFT JOIN note_content c ON c.note_id = n.id
    WHERE n.id = #{id} AND n.user_id = #{userId}
</select>
```

## 五、核心设计：自动保存的写优化

这是整个方案的技术核心，按"层层收口"的思路做四道过滤：

```
用户输入 → ① 前端防抖 → ② 内容 hash 比对 → ③ 后端 hash 比对 → ④ 乐观锁写库
             3~5s          没变不发请求        没变不写库        version CAS
```

### ① 前端防抖（拦截 90% 请求）

```ts
// 停止输入 3 秒后才触发保存，避免每敲一个字就请求
let timer: ReturnType<typeof setTimeout> | null = null
function scheduleSave(): void {
  if (timer) clearTimeout(timer)
  timer = setTimeout(() => { void doSave() }, 3000)
}
```

### ② 前端内容 hash 比对（拦截"没真改"的保存）

```ts
let lastSavedHash = ''
function doSave(): void {
  const hash = hashContent(form.content)      // 简单的字符串 hash 即可
  if (hash === lastSavedHash) return         // 内容没变，不发请求
  void noteStore.updateNote(id, form).then(() => { lastSavedHash = hash })
}
```

> 用户打开笔记、光标动了但没改内容就关掉，这类"假保存"占比很高，这一步能挡掉大部分。

### ③ 后端 hash 比对（兜底，防重复写库）

```java
public void saveNote(String id, NoteDraft draft, String userId) {
    Note note = noteMapper.selectById(id);
    checkOwnership(note, userId);                       // 归属校验

    String newHash = DigestUtils.md5Hex(draft.getContent());
    if (newHash.equals(note.getContentHash())) {        // 内容未变化
        return;                                        // 直接返回，不写库
    }
    ...
}
```

### ④ 乐观锁写入（防覆盖）

```xml
<update id="updateWithVersion">
    UPDATE note
    SET title = #{title}, summary = #{summary}, version = version + 1,
        updated_at = #{updatedAt}
    WHERE id = #{id} AND user_id = #{userId} AND version = #{expectedVersion}
</update>
```

```java
if (rows == 0) {
    throw new BusinessException("笔记已被其他设备修改，请刷新后重试", 409);
}
```

**前端 409 处理**：弹出「该笔记在其他设备有更新」提示，提供
「查看最新」/「保留我的版本」两个选项，**绝不静默丢弃用户输入**（可先存 localStorage）。

### 效果

四道过滤后，实际落库 QPS 从"理论数百"降到 **个位数到十几**，
单机 MySQL 完全无压力——这就是为什么**不需要 MQ 削峰**。

## 六、搜索方案选型

### 方案对比

| 方案 | 适用规模 | 优点 | 缺点 |
|---|---|---|---|
| `LIKE '%kw%'` | 千行以内 | 零成本 | 全表扫描，2.5 万篇必慢 |
| **MySQL FULLTEXT + ngram** | **10 万篇以内** | **零额外组件，事务一致** | 中文需配置 ngram，排序能力弱 |
| Elasticsearch | 10 万篇以上 | 分词强、高亮、聚合 | 额外运维 + 数据同步一致性 |

### 推荐：先用 MySQL 全文索引

```sql
-- my.cnf 配置中文分词（ngram token size = 2）
[mysqld]
ngram_token_size=2

-- 建全文索引
ALTER TABLE note ADD FULLTEXT INDEX ft_title_summary (title, summary) WITH PARSER ngram;
```

```xml
<select id="searchByKeyword" resultType="Note">
    SELECT id, title, summary, updated_at
    FROM note
    WHERE user_id = #{userId}
      AND MATCH(title, summary) AGAINST (#{keyword} IN NATURAL LANGUAGE MODE)
    LIMIT 20
</select>
```

**先不搜正文**（正文在 `note_content`，对它建全文索引成本高）。
若确实需要全文搜索，再考虑把正文摘要入索引，或直接上 ES。

**什么时候升级到 ES**：笔记总量超过 10 万篇、或需要搜索结果高亮/聚合/拼音搜索时。
届时才需要引入 MQ 做"笔记变更 → ES 索引同步"。

## 七、Redis 在 500 人阶段的定位

### 有真实收益的四件事（按性价比排序）

**① 限流（上线即需要）**

```java
// 保存接口：单用户 10 次/分钟，防前端异常疯狂提交
String key = "rl:save:" + userId;
Long count = redis.opsForValue().increment(key, 1);
if (count == 1) redis.expire(key, Duration.ofMinutes(1));
if (count > 10) throw new BusinessException("保存过于频繁", 429);
```

**② 缓存笔记列表（收益最大）**

```
key:    notes:list:{userId}:{category}:{page}
value:  列表 JSON
TTL:    5 分钟（或 10 分钟）
失效:   该用户新增/修改/删除笔记时 DEL notes:list:{userId}:*
```

**③ 缓存热点笔记详情**

```
key:    note:detail:{noteId}
TTL:    10 分钟
失效:   更新时 DEL
```

**④ 编辑状态提示（可选，体验加分）**

```
key:    note:editing:{noteId}  →  { "userId":xx, "device":"PC", "expire":时间戳 }
TTL:    30 秒（前端定时续期）
用途:   多端打开时提示"该笔记正在另一设备上编辑"
```

> 这就是从 50 人方案升级的关键点：**500 人规模下，读缓存的收益首次超过引入缓存的成本**。

## 八、消息队列：需要吗

**结论：500 人阶段不是必需品，但有一个场景值得考虑。**

| 场景 | 是否需要 MQ | 说明 |
|---|---|---|
| 自动保存削峰 | ❌ 不需要 | 四道过滤后仅 10+ QPS，MySQL 直接扛 |
| 浏览数统计 | ❌ 不需要 | 直接 UPDATE，或 Redis 计数定期落库 |
| **搜索索引同步** | ⚠️ **接 ES 后才需要** | 笔记变更 → MQ → ES 异步更新 |
| 异步导出（批量 Markdown） | ⚠️ 可选 | 耗时长，同步会超时才需要 |
| 操作日志 / 审计 | ⚠️ 可选 | 量大时异步落盘 |

> 如果全线使用 MySQL 全文索引（推荐方案），**MQ 可以完全不引入**。
> 引入 MQ 就要处理幂等、重复消费、堆积监控——没有明确收益时，同步调用就是最好的方案。

## 九、部署架构与高可用

### 9.1 推荐形态（500 人）

```
用户
  ↓ HTTPS
Nginx（静态资源 + 反向代理 + 限流）
  ↓
SpringBoot 实例 × 2（高可用，非性能必需）
  ↓                    ↓
Redis（缓存/限流）   MySQL 主库
                        ↓
                    MySQL 从库（只读 + 备份）
```

### 9.2 多实例的前提（你的设计已部分满足）

| 前提 | 现状 |
|---|---|
| 应用无状态 | ✅ JWT 无状态鉴权，天然满足 |
| 会话不存内存 | ✅ 令牌在客户端 |
| 文件不存本地 | ⚠️ 需改造：图片/附件必须走对象存储（COS/OSS） |
| 本地缓存不共享 | ⚠️ 若用 Caffeine，多实例间会不一致 → 改用 Redis |
| 定时任务互斥 | 当前无定时任务，暂不涉及 |

### 9.3 为什么建议 2 实例

不是为了性能（单机够），而是为了**可用性**：
一台实例重启发布或崩溃时，另一台仍能服务，用户无感知。
这是从"能跑"到"能对外服务"的分水岭。

## 十二、面试怎么讲这个项目

500 人笔记系统是很好的面试素材，建议按这条主线讲：

**1. 先展示"会算账"**（很多候选人做不到）

> "500 人在线，实际同时操作的约 100 人；自动保存防抖后约 20 QPS 写、
> 100 QPS 读。所以我判断单机 + Redis 足够，没有一上来就上分布式。"

**2. 讲清笔记系统的特殊难点**

> "笔记和简历最大的区别是**自动保存带来持续写压力**。我做了四层过滤：
> 前端防抖 → 内容 hash 比对 → 后端 hash 去重 → 乐观锁写库，
> 把落库 QPS 从数百压到十几，所以**不需要 MQ 削峰**。"

**3. 讲具体的技术决策与取舍**

- **大字段垂直拆分**：列表查询不带正文，响应从 500 KB 降到 10 KB
- **搜索选型**：2.5 万篇用 MySQL FULLTEXT + ngram，不上 ES——
  "ES 要额外维护数据同步一致性，当前规模收益不抵成本"
- **Redis 定位**："50 人时我不引入 Redis；500 人时缓存收益才超过成本"
- **乐观锁 vs 悲观锁**：编辑停留时间长、冲突少，乐观锁合适

**4. 高频追问准备**

- *Q：两人同时编辑同一篇怎么办？*
  A：区分"各自编辑自己的"和"协同编辑"。本系统是前者，用乐观锁；
  真要协同需要 OT/CRDT + WebSocket，属另一个量级，不自研。
- *Q：QPS 再高十倍怎么办？*
  A：先加 Redis 缓存扛读；写压力用批量合并；再不够考虑分库分表（按 user_id 哈希）。
- *Q：缓存和数据库不一致怎么办？*
  A：更新时删缓存（而非更新缓存），下次读回源；设置合理 TTL 兜底。
- *Q：为什么不用 MQ？*
  A：当前 20 QPS 写，同步写库完全够；MQ 会引入幂等、重复消费、堆积监控等复杂度，
  没有明确收益时同步调用最好。
