# 上线架构演进方案：从个人站到 50 人在线编辑

> 目标：支撑约 50 人在线、各自编辑/修改自己的简历与笔记。
> 撰写依据：基于当前 `back/InterViewBacked` 与 `front/InterviewProjectProject` 实际代码盘点，非泛泛而谈。

---

## 一、先说结论

**50 人在线编辑，单机 Spring Boot + MySQL 完全够用，不需要分布式。**

粗略估算：50 人在线，假设每人每分钟触发 2 次写请求、10 次读请求，
峰值约 **10 QPS 写 / 100 QPS 读**。这个量级对一台 2 核 4 G 的服务器毫无压力，
MySQL 单机轻松扛到数千 QPS，Spring Boot 单机（Tomcat 默认 200 线程）也能扛住。

所以本方案的核心不是"如何上分布式"，而是：

1. **先补齐正确性短板**（数据归属、并发覆盖、安全）—— 不做会真的出问题；
2. **再补体验功能**（草稿、历史版本、导出）；
3. **Redis / MQ / 分布式放在第三阶段**，并且明确"什么信号出现时才引入"。

> 过早引入分布式是负债不是资产：多实例带来会话一致性、分布式锁、链路追踪、
> 日志聚合等一堆新问题。面试时能讲清"**为什么现在不用**"，比堆砌技术更有含金量。

## 二、现状盘点（基于当前代码）

### 2.1 当前架构

```
浏览器(Vue3:5180) → Vite代理 → SpringBoot(:8080) → MySQL(单库)
                                  └─ JWT 无状态鉴权
```

- 后端：Spring Boot 4.0.9-SNAPSHOT + MyBatis + MySQL，单实例，无缓存、无 MQ
- 鉴权：JWT Bearer，`JwtInterceptor` 校验令牌有效性
- 数据：三表 `user` / `note` / `resume`，简历正文以 JSON 整串存在 `content` 字段

### 2.2 三个必须先解决的问题（附代码证据）

#### 问题 1：数据没有归属，存在水平越权（P0，最严重）

`schema.sql` 中 `note` 与 `resume` 表**都没有 `user_id` 字段**：

```sql
CREATE TABLE IF NOT EXISTS `resume` (
    id VARCHAR(64) NOT NULL PRIMARY KEY,
    label VARCHAR(100), path VARCHAR(200), icon VARCHAR(10),
    content LONGTEXT, created_at DATETIME, updated_at DATETIME
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4;
```

`JwtInterceptor` 解析出了 `userId` 并放进 request，但**只有 `UserController`、`AuthController`
真正使用了它**；`ResumeController` / `NoteController` 完全没用：

```java
// JwtInterceptor.java:52
request.setAttribute("userId", jwtUtil.getUserId(token));
```

后果：

- `ResumeServiceImpl.getSnapshot()` 执行 `resumeMapper.selectAll()`，**返回全库所有简历**；
- `saveResume(id, data)` / `deleteResume(id)` **不校验这条简历属于谁**。

> 也就是说：50 个用户会看到同一批简历，任何登录用户都能改、删任何人的简历和笔记。
> 这是"从个人站变成多用户系统"的第一道坎，必须先跨过去。

#### 问题 2：并发编辑静默互相覆盖（P0）

`resume` 表无 `version` 字段，`saveResume` 是**先查后全量覆盖**：

```java
// ResumeServiceImpl.java:69
public void saveResume(String id, ResumeData data) {
    Resume resume = resumeMapper.selectById(id);   // ① 读
    ...
    resume.setContent(JacksonUtils.toJson(data));  // ② 全量覆盖
    resumeMapper.update(resume);                   // ③ 写
}
```

用户 A、B 同时打开同一份简历 → A 改手机号、B 改项目经验 → 两边各自提交 →
**后提交的整份 JSON 覆盖掉先提交的**，先提交者的修改凭空消失，且没有任何提示。
这就是典型的 **lost update（丢失更新）**。

#### 问题 3：安全与运维缺口（P0/P1）

| 缺口 | 说明 |
|---|---|
| 无速率限制 | 登录接口可被暴力破解；写接口可被刷 |
| 无 HTTPS | 令牌在公网明文传输 |
| CORS 硬编码 | `WebConfig` 只放行 `localhost:5180`，上线需改；且不能配 `*` 携带凭证 |
| 无备份 | 数据库无自动备份策略 |
| 无健康检查/监控 | 服务挂了无人知晓 |
| JWT 无吊销机制 | 令牌签发后无法主动失效（登出只能前端删） |

## 三、关键澄清：两种"50 人在线编辑"不是一回事

这是本方案最重要的判断，直接决定技术选型和工期：

| | **A. 各自编辑自己的**（推荐） | **B. 协同编辑同一份**（像腾讯文档） |
|---|---|---|
| 典型场景 | 50 人各自维护自己的简历 | 多人同时改同一份简历，实时看到对方光标 |
| 冲突概率 | 极低（每人只碰自己的数据） | 极高，每敲一个字都可能冲突 |
| 技术方案 | 乐观锁 + 归属校验 | OT 或 CRDT 算法 + WebSocket 长连接 |
| 工期 | 1～2 周 | 数月，且需要专门的协同引擎 |
| 建议 | ✅ 做这个 | ❌ 不要碰 |

**结论：按 A 做。** 如果确实需要 B，不要自研，接现成的协同编辑服务
（如 Yjs + WebSocket、腾讯文档 API），那是另一个量级的项目。

## 四、第一阶段：上线必做（不做会出事）

### 4.1 数据归属改造（P0）

**① 表结构增加归属与版本字段**

```sql
ALTER TABLE `resume`
    ADD COLUMN `user_id` VARCHAR(64) NOT NULL DEFAULT '',
    ADD COLUMN `version` INT NOT NULL DEFAULT 0,
    ADD INDEX idx_user_id (`user_id`);

ALTER TABLE `note`
    ADD COLUMN `user_id` VARCHAR(64) NOT NULL DEFAULT '',
    ADD COLUMN `version` INT NOT NULL DEFAULT 0,
    ADD INDEX idx_user_id (`user_id`);
```

> 线上已有数据需要回填：把现有 3 份简历、7 篇笔记的 `user_id` 设为种子用户（admin）的 id。

**② 所有查询按用户过滤，写操作校验归属**

```java
// ResumeServiceImpl —— 读取只返回自己的
public ResumeSnapshot getSnapshot(String userId) {
    List<Resume> all = resumeMapper.selectByUserId(userId);   // 改：按 user_id 查
    ...
}

// 写操作：先校验归属，再写
public void saveResume(String id, ResumeData data, String userId, int expectedVersion) {
    Resume resume = resumeMapper.selectById(id);
    if (resume == null) throw new BusinessException("简历不存在");
    if (!resume.getUserId().equals(userId)) {                  // ← 归属校验，杜绝越权
        throw new BusinessException("无权修改该简历", 403);
    }
    ...
}
```

**③ Controller 把 userId 传下去**

```java
@PutMapping("/{id}")
public ApiResult<Void> save(@PathVariable String id,
                            @RequestBody ResumeData data,
                            @RequestAttribute("userId") String userId) {   // ← 拦截器已注入
    resumeService.saveResume(id, data, userId, data.getVersion());
    return ApiResult.ok(null);
}
```

> **注意**：`JwtInterceptor` 只对"非 GET"要求令牌，所以 `@RequestAttribute("userId")`
> 在写接口上一定取得到值。

### 4.2 并发编辑冲突：乐观锁（P0）

推荐**乐观锁**而非悲观锁：编辑停留时间长（分钟级），悲观锁会长时间占住行，
乐观锁只在提交瞬间校验，代价最小。

**实现方式：更新时带上 version 条件**

```xml
<!-- ResumeMapper.xml -->
<update id="updateWithVersion">
    UPDATE resume
    SET content = #{content}, label = #{label}, updated_at = #{updatedAt},
        version = version + 1
    WHERE id = #{id}
      AND user_id = #{userId}
      AND version = #{expectedVersion}
</update>
```

```java
int rows = resumeMapper.updateWithVersion(resume, userId, expectedVersion);
if (rows == 0) {
    // 版本号对不上 → 说明期间被别人改过
    throw new BusinessException("该简历已被其他修改，请刷新后重试", 409);
}
```

**前端配合**：捕获 409，弹窗提示"简历已被更新，是否刷新查看最新内容？"，
并保留用户当前输入（可存草稿），避免用户白写。

> 这就是"**CAS（Compare And Swap）**"思想在业务层的落地。
> 因为每人主要编辑自己的简历，真正触发 409 的概率很低，
> 用最简单的方案解决 99% 的问题，是性价比最高的选择。

### 4.3 安全加固（P0 / P1）

| 项 | 做法 | 优先级 |
|---|---|---|
| HTTPS | Nginx 配 Let's Encrypt 免费证书，全站 HTTPS | P0 |
| 登录限流 | 同 IP + 同账号失败 5 次锁定 10 分钟（可用 Bucket4j 或 Redis 计数） | P0 |
| 密码策略 | 注册密码最少 8 位且含字母数字；BCrypt 已有 ✅ | P1 |
| CORS 收敛 | `WebConfig` 改为从配置读取允许的域名，禁止 `*` | P0 |
| 令牌有效期 | JWT 设 2 小时 + 刷新令牌（redis 存刷新令牌可做吊销） | P1 |
| 敏感信息 | 配置文件用环境变量注入，仓库只提交 `application.yml.example`（已做 ✅） | P0 |
| XSS | 简历/笔记正文若用 `v-html` 渲染，需先做 HTML 白名单过滤（DOMPurify） | P1 |

### 4.4 运维与可观测（P1）

- **自动备份**：MySQL 每日全量备份（mysqldump + cron），保留 7 天，异地存储一份
- **健康检查**：Spring Boot Actuator `/actuator/health`，Nginx 或监控定期探测
- **日志**：日志文件按天切割（Logback），错误日志告警
- **监控**：最省事用云厂商自带监控（CPU/内存/磁盘），出问题能收到告警
- **进程守护**：Docker 或 systemd 保证进程崩溃自动重启

## 六、第三阶段：Redis / MQ / 分布式——什么时候才需要

### 6.1 Redis：按收益排序的四种用法

| 用法 | 何时引入 | 当前是否需要 |
|---|---|---|
| **缓存热点读**（简历快照、笔记列表） | 读 QPS 上千、DB 压力大 | ❌ 现在不需要，100 QPS MySQL 毫无压力 |
| **分布式会话 / 令牌吊销** | 需要"强制下线""单设备登录" | ⚠️ 可选，看产品需求 |
| **分布式锁**（防重复提交、定时任务互斥） | 多实例部署后 | ❌ 单实例用 JVM 锁即可 |
| **限流计数** | 上线即需要（防刷登录） | ✅ 可用 Redis，也可先用本地 Guava RateLimiter |

> **关键认知**：引入 Redis 的**最大收益其实不是性能，而是把"状态"从应用里挪出去**，
> 从而让应用可以水平扩展。单实例阶段它的性能收益接近于零。

### 6.2 消息队列：典型适用场景

MQ 解决的是**异步解耦 + 削峰填谷**。当前系统里真正适合的场景：

| 场景 | 说明 | 当前是否需要 |
|---|---|---|
| 导出 PDF 异步化 | 提交任务 → 返回任务 id → 完成后通知下载 | ⚠️ 用户量上来再做 |
| 浏览数/统计计数 | 高频写计数，先写 MQ 再批量落库 | ❌ 50 人量级直接写库即可 |
| 操作日志 / 审计 | 记录谁改了什么，异步落盘 | ⚠️ 可选 |
| 邮件/短信通知 | 注册欢迎、密码重置 | ⚠️ 有需求再说 |
| 搜索索引同步 | 接入 Elasticsearch 后同步数据 | ❌ 未引入搜索 |

> **不要为了用 MQ 而用 MQ**。50 人系统引入 MQ 会增加：消息丢失/重复消费/
> 顺序性/幂等性/堆积监控等一整套复杂度。同步调用能解决时，同步就是最好的方案。

### 6.3 真正的分布式：什么时候上多实例

**前提条件（缺一不可）**：

1. **应用无状态** —— 这一点当前设计**已经满足** ✅
   JWT 是无状态鉴权，用户会话不存服务端内存，天然支持多实例。
2. **文件不存本地** —— 头像/附件必须放对象存储（COS/OSS），否则多实例间看不到
3. **定时任务不能重复执行** —— 用分布式锁或 XXL-Job 等调度中心
4. **WebSocket 需处理会话共享** —— 长连接要配合 Redis Pub/Sub 广播

**架构形态**：

```
                    ┌─ SpringBoot 实例 1 (:8081)
用户 → Nginx(:443) ─┼─ SpringBoot 实例 2 (:8082)  → MySQL(主) ─→ MySQL(从,只读)
      负载均衡      └─ SpringBoot 实例 3 (:8083)       │
                                                      └→ Redis(共享状态/锁/限流)
```

**何时才需要**：单机 CPU 持续 > 70%、或需要"不停机发布"、或要求高可用（一台挂了还能服务）。
50 人规模**触发不了这些条件**。

### 6.4 一表总结：什么阶段用什么技术

| 技术 | 现在（个人/内测） | 50 人上线 | 未来 5000 人 |
|---|---|---|---|
| 部署 | 直接 `java -jar` | Docker Compose 单机 | K8s / 多机 |
| 数据库 | 单 MySQL | 单 MySQL + 每日备份 | 主从读写分离 |
| 缓存 | 无 | 无（或仅限流） | Redis 集群 |
| 锁 | JVM 锁 | 乐观锁（version） | Redisson 分布式锁 |
| MQ | 无 | 无 | RabbitMQ / Kafka |
| 文件 | 本地 / 不存 | 对象存储 COS | 对象存储 + CDN |
| 监控 | 无 | Actuator + 云监控 | Prometheus + Grafana |

## 八、面试怎么讲这个项目

这个项目的价值不在"用了多少中间件"，而在**能否讲清楚取舍**。建议按这条主线讲：

1. **从 0 到 1 的完整链路**：需求 → 接口设计 → 前后端分离 → 联调 → 上线，闭环能力
2. **遇到的真实问题**：Jackson 3 包名变更、Maven 镜像拦截快照、沙箱端口冲突、前后端权限收口
3. **架构演进的判断力**（最能拉开差距）：
   - "50 人规模我**没有**引入 Redis 和 MQ，因为单机足以支撑，引入反而带来分布式事务、
     缓存一致性、消息幂等等复杂度"
   - "我把精力放在**数据归属校验**和**乐观锁防覆盖**上，因为这是多用户系统真正会出事的地方"
   - "应用一开始就用 JWT 做**无状态鉴权**，所以未来要水平扩展时不需要改造会话"
4. **自己发现的坑**：主动提到"我发现原设计里所有人共享同一批简历、且写操作不校验归属，
   我通过增加 `user_id` + 乐观锁解决"——这比背八股文有说服力得多

> 面试官高频追问准备：
> - 乐观锁和悲观锁怎么选？→ 编辑场景停留长、冲突少，乐观锁合适
> - 为什么不用 Redis 做缓存？→ 100 QPS 下缓存收益为负，还引入一致性问题
> - 令牌怎么吊销？→ 短期 JWT + 刷新令牌存 Redis，或维护令牌黑名单
> - 多人协同编辑怎么做？→ 区分"各自编辑"与"协同编辑"，后者需 OT/CRDT，不自研
